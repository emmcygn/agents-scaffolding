LexiChunk Scaffolder

Evaluation harness & interactive research tool proving that legal-aware chunking measurably improves RAG retrieval quality over general-purpose alternatives.

Target:  SDK effectiveness proof Audience:  80% external demos / 20% self-validation Outputs:  CLI + JSON + HTML + Streamlit dashboard Repo:  sdk-scaffolder (standalone)

03Pipeline Flow — Left to Right

Each stage of the evaluation pipeline, what it does, its inputs/outputs, and which phase delivers it.

Stage Component Input Process Output Phase
1. Ingest FixtureManager 5 built-in .txt files, user uploads, or LegalBench-RAG corpus Load, validate, detect jurisdiction, assign document ID. Extensible registry for adding new fixtures. Document objects with metadata 1a
2. Chunk ChunkingPipeline Document objects Run each document through all registered strategies in parallel. Strategies: LexiChunk (clause-aware), RCTS (LangChain default), sentence-split, fixed-size (256/512/1024 tokens). ChunkSet per strategy per document (chunks + timing + metadata) 1a
3. Structural Eval StructuralMetrics ChunkSet objects Compute clause fragmentation rate (% chunks splitting mid-clause), definition preservation (% defined terms accessible), cross-ref resolution rate, avg hierarchy depth, chunk size distribution. StructuralReport per strategy 1a
4. Embed EmbeddingPipeline ChunkSet objects Embed all chunks using selected model(s). Local models via sentence-transformers. Paid models (Voyage) via API with toggle. Caches embeddings to disk for re-runs. Embedding vectors per chunk, persisted in .cache/ 1b
5. Index VectorIndex Embedding vectors Build FAISS flat L2 index per strategy per embedding model. Supports incremental updates. FAISS indices ready for querying 1b
6. Query RetrievalSimulator Curated query set + FAISS indices For each query: embed query, retrieve top-k from each strategy's index, record retrieved chunks and ranks. Queries have known-relevant chunk annotations. RetrievalResult per query per strategy 1b
7. Retrieval Eval RetrievalMetrics RetrievalResult objects Compute Precision@k, Recall@k, MRR, NDCG@10 per strategy. Run paired t-tests for statistical significance between LexiChunk and each baseline. RetrievalReport with per-query and aggregate scores 1b
8. LLM Judge LLMEvaluator Retrieved contexts + queries Feed top-k context + query to GPT-4o-mini via DeepEval. Score faithfulness (target >0.9) and answer relevancy. Toggled off by default; runs on configurable subset. FaithfulnessReport 3
9. Report ReportGenerator All metric reports Aggregate results into three formats: CLI summary (rich tables), JSON (machine-readable), HTML (standalone page with charts). Comparison tables, per-document breakdowns, statistical significance markers. CLI stdout, results.json, report.html 1b
10. Dashboard Streamlit App All pipeline components Interactive multi-page app: upload docs, compare chunking side-by-side, run retrieval queries live, drill into metrics, switch embedding models. Web UI at localhost:8501 2

06Metrics Framework

Two complementary metric families grounded against industry standards.

Structural Quality Metrics (Phase 1a — no embeddings needed)

These prove LexiChunk chunks correctly. Computed deterministically, zero cost.

Metric What It Measures Grounded Against LexiChunk Advantage
Clause Fragmentation Rate % of chunks that split a clause mid-boundary Reuter et al. (NLLP 2025): structural chunking scored 0.59 nDCG vs 0.244 for fixed-size LexiChunk's clause-aware strategy should approach 0% fragmentation
Definition Preservation Rate % of defined-term usages where the definition is accessible (in same chunk or linked metadata) Anthropic Contextual Retrieval: 35% reduction in retrieval failure with chunk context LexiChunk extracts + propagates definitions; baselines cannot
Cross-Reference Resolution Rate % of detected cross-references resolved to target chunks No existing benchmark (this IS the novelty). EU regulation graph study had 3,600+ edges LexiChunk's cross-ref detector + resolver; baselines score 0%
Hierarchy Depth Retained Avg hierarchical path depth per chunk (e.g., Article VII → Section 7.2 → 7.2(a) = depth 3) Ferraris et al. multi-layered retrieval validated hierarchical approach LexiChunk preserves full hierarchy path; baselines have depth 0
Chunk Size Distribution Mean, median, std dev, min/max tokens per strategy Best practice: 512–1024 tokens for legal text; larger overlap for cross-ref-heavy docs LexiChunk respects natural clause boundaries; baselines produce uniform/arbitrary sizes
Clause Type Coverage % of chunks classified into a legal clause type with confidence > threshold LexiChunk's 24+ clause type classifier; unique in open-source Enables filtered retrieval ("find all indemnification clauses")

Retrieval Quality Metrics (Phase 1b — requires embeddings)

These prove LexiChunk chunks retrieve better. The real claim.

Metric What It Measures Industry Standard Implementation
Precision@k % of top-k retrieved chunks that are relevant RAGAS Context Precision; MLEB standard metric k = {1, 3, 5, 10}. Relevance from query annotations.
Recall@k % of all relevant chunks captured in top-k RAGAS Context Recall; critical for legal completeness k = {1, 3, 5, 10}. Higher weight than precision for legal (missing a clause is worse than extra noise).
MRR Mean reciprocal rank of first relevant result Standard IR metric; used in LegalBench-RAG Computed per-query, averaged across query set.
NDCG@10 Ranking quality with graded relevance Primary metric in MLEB (Massive Legal Embedding Benchmark) Graded relevance: exact clause match = 3, same section = 2, related = 1.
DRM Rate % of queries where top-1 chunk comes from wrong document Reuter et al.: >95% DRM with naive chunking on similar legal docs Test with structurally similar fixtures (2 UK docs, 2 US docs).
Statistical Significance Whether improvements are statistically meaningful Paired t-test standard for IR evaluation Per-query paired t-test, LexiChunk vs each baseline, p < 0.05.

LLM-Judge Metrics (Phase 3 — toggled, paid API)

Metric What It Measures Target Cost
Faithfulness % of generated claims supported by retrieved context >0.9 (legal requires higher than general; Stanford found 17–33% hallucination baseline) ~$10–15 for 100 queries via GPT-4o-mini
Answer Relevancy How relevant generated response is to query >0.8 Included in same API calls

07Query Strategy

Two tiers of queries that test exactly what LexiChunk claims to improve.

Tier 1: Curated Queries Against 5 Fixtures (Phase 1b)

Hand-annotated queries with known-relevant sections. Tests the five failure modes LexiChunk addresses:

Failure Mode Tested Example Query Fixture Why Baselines Fail
Clause fragmentation "What are the termination provisions?" UK Service Agreement RCTS splits the termination clause across 2–3 chunks; retrieved chunk is incomplete
Orphaned cross-references "What exceptions apply to the limitation of liability?" US MSA Exceptions are in a schedule referenced by "subject to Schedule 3"; baselines lose this link
Lost defined terms "Define 'Material Adverse Effect'" US MSA Definition is in Section 1; usage is in Section 7; baselines separate them completely
Destroyed hierarchy "What obligations does the service provider have under clause 4?" UK Service Agreement Without hierarchy metadata, embedding search can't scope to clause 4 specifically
Cross-document contamination "What is the governing law for the UK agreement?" Multi-document (UK + US) Both docs have "Governing Law" sections with similar embeddings; DRM pulls wrong doc

Target: ~15–25 curated queries across the 5 fixtures, each annotated with the exact relevant section(s). Stored as YAML in queries/.

Tier 2: LegalBench-RAG (Phase 3)

6,858 queries with character-level ground truth. The gold standard for publication-grade results. Mini version (776 queries) for rapid iteration. Used alongside LLM-judge evaluation for the complete picture.

08Key Tradeoffs

Decisions made and the reasoning behind them.

Standalone repo vs folded into LexiChunk

Standalone (for now)
Pros of standalone Separation of concerns — SDK is the tool, scaffolder is the proof. Can benchmark other chunkers without polluting SDK. Different dependency profile (sentence-transformers, faiss, streamlit are heavy). Independent release cycle.
When to fold in If the benchmark harness stabilises and the core metrics become part of LexiChunk's CI quality gates, the metrics/ and chunking/ modules could move into lexichunk/benchmarks/. The Streamlit dashboard should always stay separate.

Custom metrics vs RAGAS/DeepEval library

Custom first, DeepEval for LLM-judge
Why custom for retrieval P@k, R@k, MRR, NDCG are 10–20 line functions. Using RAGAS bundles in an LLM-judge dependency we don't want in Phase 1. Custom means zero API cost for deterministic metrics and full control over the evaluation loop.
Why DeepEval for LLM-judge pytest-native (fits CI pipeline), well-maintained, supports GPT-4o-mini. When Phase 3 turns on the paid toggle, DeepEval gives us faithfulness + answer relevancy without building a judge from scratch.

Streamlit vs Gradio

Streamlit
Streamlit wins because Multi-page navigation (upload → compare → retrieve → metrics). Native dataframe/chart support. More professional dashboard aesthetic. Better for complex layouts. Free deployment via Streamlit Community Cloud.
Gradio would win if This were a simple "upload → see result" demo (Gradio excels there). Or if HuggingFace Spaces deployment were critical (Gradio is native). We may later add a lightweight Gradio demo for HF Spaces alongside the full Streamlit dashboard.

Embedding model selection

2 local free + 1 paid toggled
Why multiple models MLEB benchmark shows legal-specific rankings diverge dramatically from general MTEB. Using 3 models proves results generalise. all-MiniLM (fast baseline) + bge-base (strong mid-tier) run locally for free. Voyage Law 2 (legal-specific, best in class) is the paid option.
Risk sentence-transformers is a large dependency (~500MB with torch). Mitigated by making it a pip extra: pip install scaffolder[local] vs pip install scaffolder[voyage]. Core harness works without either.

FAISS vs ChromaDB vs Qdrant

FAISS
FAISS because Deterministic (flat L2 index gives identical results every time). No server process. Academic standard for IR benchmarks. Fast enough for our corpus size. Single faiss-cpu dependency.
ChromaDB/Qdrant would add Persistence, filtering, metadata queries. Not needed for benchmarking — we control the entire pipeline. If the Streamlit dashboard needs richer querying later, ChromaDB could be added as an optional backend.

5 fixtures vs LegalBench-RAG from the start

5 fixtures first, LegalBench-RAG in Phase 3
Why 5 fixtures first Hand-annotated queries let us test exact failure modes (the 5 gaps LexiChunk addresses). Faster iteration. Results are interpretable — you can look at the actual document and verify. Good for demos ("here's a real UK service agreement, watch what happens").
Why LegalBench-RAG later 6,858 queries is publication-grade scale. Best deployed once the pipeline is stable and we're confident in results. Character-level ground truth means we can compute Token-IoU — but only worth the effort when preparing blog post / formal benchmark numbers.

LLM-judge always-on vs toggled

Toggled off by default
Why toggled Costs real money (GPT-4o-mini API calls). Non-deterministic — different runs may give different scores. The deterministic retrieval metrics (P@k, MRR, NDCG) are the primary proof. LLM-judge adds qualitative depth but shouldn't be a development dependency.
When to turn on Phase 3, once deterministic metrics look strong. Run on 100-query subset. Results go into blog post and formal benchmark. Budget: ~$10–15 per full run.

09Grounding Against Best Practices

How each design decision maps to production legaltech RAG standards.

Best Practice (Source) What It Says How We Implement It
RAGAS Framework
EACL 2024		 Evaluate retrieval with Context Precision + Recall; evaluate generation with Faithfulness + Answer Relevancy. 95% human agreement on faithfulness. Phase 1b: deterministic P@k/R@k (no LLM needed). Phase 3: DeepEval faithfulness + answer relevancy (RAGAS-aligned). Two-phase approach avoids premature API spend.
MLEB Benchmark
Oct 2025		 Legal-specific embeddings dramatically outperform general models. Kanon 2 (#1), Voyage 3 Large (#2), Voyage Law 2 (#8) all beat OpenAI. General MTEB rankings don't predict legal performance. Include Voyage Law 2 as paid toggle. Test with multiple models to prove results generalise. Explicitly document that model choice matters for legal retrieval.
LegalBench-RAG
arXiv 2408.10343		 First legal RAG benchmark. 6,858 queries with character-level ground truth. Chunking strategy significantly affects retrieval quality. Rerankers can hurt legal retrieval. Phase 3: full LegalBench-RAG evaluation. Phase 1b: aligned methodology (character-level relevance annotations on our 5 fixtures).
Summary-Augmented Chunking
Reuter et al., NLLP 2025		 Prepending 150-char document summaries reduces DRM by ~50%. Generic summaries outperform expert-guided legal summaries. LexiChunk's context headers are analogous to SAC. We measure whether context-enriched chunks improve retrieval vs raw chunks.
Anthropic Contextual Retrieval
Sep 2024		 Adding 50–100 tokens of chunk-specific context before embedding reduced top-20 retrieval failure by 35% (67% with BM25 + reranking). LexiChunk's build_embedded_text() adds context headers. We benchmark with and without context enrichment to quantify the improvement.
Document-Level Retrieval Mismatch
Reuter et al., NLLP 2025		 >95% DRM with naive chunking on structurally similar legal documents. The #1 failure mode for multi-document legal RAG. Explicit DRM metric. Test with structurally similar fixtures (2 UK docs, 2 US docs). LexiChunk's document_id metadata should eliminate DRM.
Stanford Legal RAG Hallucinations
2025		 Commercial legal RAG tools (Lexis+ AI, Westlaw AI) hallucinate 17–33% of the time. Faithfulness >0.9 is the target for legal. Phase 3 LLM-judge targets faithfulness >0.9. We can cite Stanford's baseline as context: "commercial tools hallucinate 17–33%; our pipeline achieves X%".
LangSmith Evaluation
LangChain		 Production RAG evaluation should separate retrieval quality from generation quality. Support human eval, heuristic checks, LLM-as-judge, and pairwise comparison. We do exactly this: structural metrics (heuristic), retrieval metrics (deterministic), LLM-judge (Phase 3). Pairwise comparison is the side-by-side Streamlit view.

11Extensibility Roadmap (Summary)

To be detailed in the standalone EXTENSIBILITY.md design doc.

Adding New Fixtures

Drop a .txt file into fixtures/documents/, add a matching .yaml query file in queries/ with annotated relevant sections. FixtureManager auto-discovers new files. README in queries/ documents the annotation schema.

Adding Chunking Strategies

Implement the ChunkingStrategy protocol (a chunk(text, document_id) → List[Chunk] method). Register in strategies.py. Automatically included in all benchmarks and comparisons.

Adding Embedding Models

Implement the Embedder protocol (embed(texts) → ndarray). Local models via sentence-transformers adapter. API models via custom adapter (Voyage pattern as reference). Toggle via config.

Adding Metrics

Structural metrics: add a function to structural.py that takes ChunkSet → float. Retrieval metrics: add to retrieval.py with the same (retrieved, relevant) → float signature. Auto-included in reports.

Adding Query Sets

YAML format with query text, fixture reference, and list of relevant section identifiers. Supports graded relevance (exact match = 3, same section = 2, related = 1) for NDCG computation.

Future: LegalBench-RAG Integration

Phase 3 adds a dataset loader that pulls LegalBench-RAG from HuggingFace, converts character-level annotations to our query format, and runs the full pipeline. Same evaluation code, larger dataset.
